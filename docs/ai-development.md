# AI 開発体制

実装は AI（Claude Code）に任せ、人間は PR を動作確認してマージする。本番デプロイは人間が行う。

## 流れ

1. 人間が依頼する。小さくない依頼は「まず方針だけ出して」と頼み、方針を確かめてから実装させる
2. AI が実装し、`pnpm build`（用意できたあとは `pnpm test` と `pnpm typecheck` も）を通し、`/code-review high` でセルフレビューしてから PR を作る。PR 本文は `.github/pull_request_template.md` の欄で書く
3. 人間が PR の「確認してほしいこと」に沿って動作を確かめ、マージする

## ルールの置き場所

強制力の強い順に使う。AI に守らせたいことは、まず上の手段で書けないかを考える。

| 手段 | 向いている内容 |
| --- | --- |
| CI / lint | 機械で判定できること |
| `AGENTS.md`、`.claude/rules/` | 短いプロジェクト固有のルール。毎回読まれるので、コードを読めばわかることは書かない |
| スキル | 長い手順や、モデルが知らない知識 |

自作のスキルやサブエージェントは、必要になるまで作らない。

## 見落としの記録

AI のレビューが見落としたものや、妥当でない設計に気づいたら、PR にコメントを残すか `review-miss` ラベルの Issue にする。溜まったら次の順で対策する。

1. 機械で判定できる → CI か lint に入れる
2. 短いルールで防げる → `AGENTS.md` に 1 行足す
3. 同じ種類を繰り返す → AI レビューの観点にする

## 未整備

旧リポジトリ（`sendo-kakeru/bowling-lab_old`）にあったものは、そこから移植できる。

- [ ] Biome（旧リポジトリの `biome.json`）。入れたら `.claude/rules/coding.md` の「Biome を入れるまでの間だけ書いておくもの」を消す
- [ ] CI（lint、型チェック、ユニットテスト、ビルド。旧リポジトリの `.github/workflows/`）
- [ ] Renovate（旧リポジトリの `renovate.json`）と、Node / pnpm のバージョン固定（`mise.toml`）
- [ ] デプロイと、PR ごとのプレビュー URL の発行（動作確認だけでマージする前提）
- [ ] AI レビューの GitHub Actions ワークフロー。API キーをリポジトリのシークレットに登録してから作る
- [ ] 表示の差分比較（ページのスクリーンショット）と、全ページのスモークテスト

ブランチ保護は、private リポジトリでは GitHub Pro 以上が必要なので使っていない。CI ができたら、マージ前に人間が CI の結果を見る。
